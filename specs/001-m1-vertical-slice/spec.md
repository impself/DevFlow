# Feature Specification: M1 主线竖切——Issue 接收到有据答复与批准发布

**Feature Branch**: `001-m1-vertical-slice`

**Created**: 2026-09-01

**Status**: Draft

**Input**: User description: "M1 主线竖切：Webhook 接收自有测试仓库的 Issue 事件 → 建立持久化 Run（任务领取/心跳/租约最小版）→ Issue Agent 生成带引用的答复草稿 → 最小任务界面人工审阅与批准 → 向该 Issue 精确发布一条评论（POST_ISSUE_COMMENT）"

本切片对应 PRD 里程碑 **M1：可信接入与回答**（PRD §27.2），是 DevFlow 的第一条
端到端主线：从真实 GitHub Issue 进入，到操作者批准后对外发布一条有依据的评论，
全程"批准前零写入"。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 测试 Issue 自动生成有依据的答复草稿 (Priority: P1)

维护者在已接入的自有测试仓库创建一个"文档已有答案"的用法类 Issue（B01 类场景）。
系统自动接收事件、建立处理上下文，读取固定版本的文档与源码，生成带出处引用的
答复草稿。操作者随后能在任务界面看到草稿、每条引用的来源定位，以及原始事件记录。

**Why this priority**: 这是 M1 里程碑的退出主线（"一条真实测试 Issue 自动生成有依据
答复"）；没有它，后续审批与发布无从谈起。

**Independent Test**: 在测试仓库创建一个 Issue，稍后在任务界面看到带引用的答复草稿；
全程 GitHub 上无任何写入。可独立演示、独立验收。

**Acceptance Scenarios**:

1. **Given** 已完成接入且权限齐全的测试仓库，**When** 创建一个文档可答的 Issue，
   **Then** 系统持久化原始事件、建立 Case 与 Run，并生成引用固定源码/文档版本的
   答复草稿；此时 GitHub 上没有新增任何评论（AC03、AC31）
2. **Given** 同一事件被平台重投，**When** 再次收到相同投递标识的 Webhook，
   **Then** 原始事件只保留一条，不重复创建 Run（AC45）
3. **Given** Issue 描述不足以给出答案（B03/B04 类），**When** 分析完成，
   **Then** 输出 NEEDS_INFO 结论与至多 3 个有帮助的追问，Run 正常结束并释放执行槽，
   不猜测根因（AC04）
4. **Given** 仓库接入时缺少必需的读取权限，**When** 操作者尝试接入，
   **Then** 界面展示缺失的具体能力，不创建伪成功连接，也不启动分析（AC01）

---

### User Story 2 - 操作者批准后精确发布一条评论 (Priority: P1)

操作者在任务界面审阅答复草稿与证据，点击批准。系统向目标 Issue 发布与批准内容
完全一致的一条评论；重复点击批准或网络重试都不会产生第二条；发布结果可核对。

**Why this priority**: M1 要验证的主线是"人工控制对外发布"；评论发布也必须具备身份、
批准、幂等和结果核对，不能因为完整发布器在 M4 扩展就先绕过边界（PRD §27.2）。

**Independent Test**: 批准一条草稿 → 测试仓库的该 Issue 恰好新增一条与批准内容一致的
评论；重复批准与重启重试后评论数不变。

**Acceptance Scenarios**:

1. **Given** 答复草稿已生成但未经批准，**When** 任何人（包括系统自身）未执行批准，
   **Then** GitHub 上始终无新增评论、分支或 PR（AC31）
2. **Given** 授权操作者在界面上批准了精确的评论内容与目标，**When** 系统执行发布，
   **Then** 只创建一个发布动作并发出一条评论；同一批准被重复提交时返回同一结果，
   不创建新的发布批次（AC32、AC35）
3. **Given** 发布请求已发出但响应超时、结果不明，**When** 系统执行核对，
   **Then** 进入核对状态，按目标、身份与内容核对远端结果；不确定时转人工处理，
   不盲目重发第二条（AC36）
4. **Given** 审批后有人修改了评论文字或目标，**When** 再次提交发布，
   **Then** 原批准失效，必须生成新的审批包重新批准（AC33）
5. **Given** 未授权的操作者身份提交批准，**When** 请求到达系统，
   **Then** 被认证/授权层拒绝，使用服务端身份而非请求声明，不创建任何执行中的
   发布动作（AC32）

---

### User Story 3 - 任务与恢复的最小可见性 (Priority: P2)

操作者能在最小工作台看到 Case 与 Run 的状态、来源 Issue、答复草稿、原始事件记录
和调用花费。分析进程在执行中途崩溃后，系统在租约到期后自动恢复，已确认的结果
不丢失，未提交的结果不伪装完成。

**Why this priority**: M1 退出条件要求"原始事件与 Trace 可查"和"Run 最小状态与租约"；
恢复能力是 DevFlow 与一次性脚本的分界线，但相对前两个故事可稍后完善。

**Independent Test**: 在分析进行中重启执行进程 → 观察租约到期后任务被接管恢复，
GitHub 无重复写入，界面状态与实际一致。

**Acceptance Scenarios**:

1. **Given** 一个 Run 正在执行，**When** 执行进程在节点中途崩溃，
   **Then** 租约到期后系统从已提交状态恢复；未提交的部分结果不伪装为完成（AC23）
2. **Given** 崩溃的旧进程恢复并尝试写回结果，**When** 它携带旧的租约纪元提交状态，
   **Then** 提交被拒绝，不能覆盖新状态（AC24）
3. **Given** 操作者打开任务界面，**When** 查看任一 Case，
   **Then** 能看到来源 Issue、Run 状态轨迹、原始事件记录、答复草稿与本次分析的花费
   记录（M1 退出条件、AC47）

---

### Edge Cases

- Issue 在分析期间被编辑或关闭：Run 以固定输入快照为准；内容变化使在途结果标记为
  过期，不悄悄采用新内容，也不向已关闭的 Issue 发布（§16.4、AC34 精神）
- 机器人自己发布的评论再次触发事件：正确识别并去重，不形成自触发循环（AC45）
- 模型调用超时而供应商可能已计费：费用记为待确认/估算，不记为零（AC47）
- GitHub App 被卸载或存储不可用：停止对应新执行并展示明确原因，不写出成功形状的
  假结果（AC50）
- 收到范围外仓库或不支持的事件类型：记录并忽略，不误触发分析
- 批准包超过有效期后才执行发布：拒绝执行并要求重新批准（PRD §15.2）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-1**: 系统 MUST 支持操作者接入自有 GitHub 测试仓库，展示仓库数字 ID、owner、
  默认分支与实际具备的能力；能力缺失时 MUST 明确报错，不得伪装接入成功
  （对应 PRD FR-01；AC01）
- **FR-2**: 系统 MUST 订阅 issues opened / reopened 事件；收到事件 MUST 先验证签名、
  限制载荷大小并持久化原始记录，再快速响应；相同投递标识只保留一条原始记录，
  且投递去重与业务触发去重必须分开（对应 PRD FR-02；AC45）
- **FR-3**: 每次分析 MUST 建立针对固定输入快照（Issue 内容版本 + 仓库固定 SHA）的
  Run，具备任务领取、心跳与租约（默认心跳 5 秒、租约 30 秒）；Run MUST 支持
  排队、执行、恢复、完成、失败、取消的最小状态集；执行者崩溃后 MUST 能在租约
  到期后恢复，旧执行者的迟到提交 MUST 被拒绝（对应 PRD FR-11 最小版；AC23、AC24）
- **FR-4**: 对文档可答的用法/配置类 Issue，系统 MUST 生成包含证据引用的答复草稿，
  每条引用含来源定位（文档位置、代码文件与行号）与固定的仓库版本；文档与实现
  冲突时 MUST 同时呈现冲突，不得只选一个来源（对应 PRD FR-03/FR-04；AC03）
- **FR-5**: 输入不足以回答时，系统 MUST 输出"需要补充信息"结论与至多 3 个追问，
  不猜测根因，不开启代码修改（对应 PRD FR-03；AC04）
- **FR-6**: 本切片对外动作 MUST 仅支持"发布 Issue 评论"一种；发布前 MUST 生成包含
  精确目标（仓库、Issue）与最终内容摘要的审批包；审批包有效期 24 小时
  （对应 PRD FR-12 最小版；AC31–AC33）
- **FR-7**: 发布 MUST 仅能由服务端认证的授权操作者触发；同一审批包的重复提交
  MUST 幂等返回同一结果；发布响应丢失 MUST 通过核对远端结果解决，不得直接重发
  （对应 PRD FR-12；AC32、AC35、AC36）
- **FR-8**: 发布执行前系统 MUST 重新核对目标 Issue 未关闭、无新的相关回复、
  草稿仍然适用；不满足时停止发布并说明原因（PRD §4.2）
- **FR-9**: 系统 MUST 提供最小任务界面：Case/Run 列表、任务详情（输入快照、
  答复草稿、引用证据、审批入口）、原始事件与调用 Trace 可查（对应 PRD FR-14 最小版；
  M1 退出条件）
- **FR-10**: 系统 MUST 记录每次模型调用的模型标识、用量与费用（无法确认时记为
  估算/待确认，不得记零），并关联到所属 Run 与 Case（对应 PRD FR-15 最小版；AC47）

### Key Entities *(include if feature involves data)*

- **Repository（已登记仓库）**: 操作者接入的自有测试仓库，及其经确认的访问能力
  与策略；仓库以数字 ID 标识，不以可重命名的名称为准
- **InboxEvent（原始事件）**: 一次已验证、已持久化的 GitHub 投递记录，含投递标识
  与签名验证结果；是所有后续处理的可追溯起点
- **Case**: 围绕一个 Issue 的长期处理上下文，跨 Run 保留
- **Run**: 针对固定输入快照的一次有预算执行；含状态、租约纪元与最终结论
  （答复就绪 / 需要信息 / 未解决等）
- **Evidence（证据）**: 带来源、版本、定位与内容摘要的引用；没有出处的模型解释
  不构成证据
- **ReplyDraft（答复草稿）**: 引用证据组织而成的对外内容草稿，及其内容摘要
- **ApprovalBundle（审批包）**: 一组精确的外部动作 + 目标 + 内容摘要 + 有效期 +
  操作者决定；审批对象是精确内容，不是抽象任务
- **Action（外部动作）**: 一次明确的 GitHub 写操作实例，含执行状态与远端核对结果

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-1**: 一条真实测试 Issue 从创建到生成可审阅的答复草稿全程无需人工干预，
  草稿中的每条引用都能人工核对到固定版本的文档或代码位置（M1 退出条件）
- **SC-2**: 未批准时 GitHub 侧保持零写入；批准后目标 Issue 恰好新增一条与批准内容
  一致的评论；在重复批准、进程重启、响应超时三类扰动下评论数不变
- **SC-3**: 分析进程在执行中途被终止后，系统在租约到期后自动恢复并继续完成，
  已确认结果不丢失、不重复发布（AC23/AC24 验证）
- **SC-4**: 事件接收在 1 秒内完成持久化并响应，始终遵守平台要求的响应窗口；
  数据库不可用时返回失败而不是先确认后丢失（PRD §16.3、§26.2 目标）
- **SC-5**: 每次分析结束后，操作者能在界面查到原始事件、Run 状态轨迹与本次模型
  调用费用记录（含估算标记）

## Assumptions

- 首个目标仓库是自建的 `devflow-fixture` Python 仓库（独立建仓、规模 ≤5000 行、
  文档足以回答 B01 类用法问题）；其建仓规格是独立 spec，不在本切片内
- 单操作者使用 GitHub App installation 认证，按最小权限申请（Metadata/Contents/Issues
  读取 + Issues 写入用于评论发布）
- 自动修复（补丁）、隔离执行容器、动态 DAG、分支发布与 Draft PR 均不在本切片范围
  （M2+ 交付）；Run 内任务结构保持最小，不预先建设完整编排引擎
- B01–B05 答复类案例是本切片的主要验证素材；评测集冻结与三策略对照在 M5
- 开发环境为本地 Windows + Linux 虚拟化；数据库与执行资源在本地启动即可满足单操作者
  并发 1–2 个 Run 的验证需求
